# 无用 Agent 系列之快递员：我想先做一个看起来没什么用的职业 Agent

有些项目，第一眼看上去就不像正经产品。

比如这次我想做的东西：一个快递员 Agent。

不是快递公司的派单系统，不是路径规划算法，也不是那种写死状态流的业务 demo。它的目标更奇怪一点：让一个大模型扮演快递员，自己读业务规则，自己判断现在遇到了什么情况，自己决定要不要调用工具，然后把每一次决策都记录下来。

听起来有点无用。

快递员这个职业，现实里当然不可能靠一个 demo 取代。它有路况、天气、小区门禁、客户电话、平台规则、异常赔付，还有很多线下经验。一个模型坐在 FastAPI 后面，连电动车都不会骑。

但我反而觉得，这正是它适合当开篇的原因。

因为职业 Agent 这件事，最值得研究的不是“AI 能不能替代一个人”，而是另一个更工程化的问题：**当一个职业被拆成规则、工具、记忆、事件和决策之后，我们能不能把它做成一个可运行、可观察、可复盘的系统？**

这就是「无用 Agent 系列」的第一篇。

我打算从快递员开始。

---

## 01 我最开始给 AI 的指令

这个项目的起点很简单。

我给 AI 的大概指令是：

> 这是一个空项目。帮我搜索一下，现在用 Python 框架做职业 Agent，应该怎么规划一个 demo。比如把快递员做成 Agent。它能不能 long run，能不能 HeartBeat 长时间运行？

AI 一开始给出的方案，其实比较像传统系统设计：状态机、任务流、派单、取件、送达、异常处理。

这些东西当然有用，但我很快意识到，这不是我真正想要的。

于是我又补了一句：

> 我们要使用大模型来实现 Agent，并不是传统的固定处理流。它可以自行判断使用工具，并且拥有自己的业务工作规则，处理各种情况的手册或规则。

这句话很关键。

因为很多所谓 Agent 项目，本质上还是流程引擎。它只是把“下一步做什么”包装成了模型调用，但真正的决策仍然写死在代码里。

我想要的不是这个。

我想要的是：快递员 Agent 收到一个事件，比如“客户不接电话”“电量只剩 12%”“小区门禁打不开”“包裹已取件”，它可以先去查自己的配送手册，再决定是联系客户、通知调度、重新规划路线，还是把订单标记为异常。

它不是乱想。

它要在规则里行动。

---

## 02 AI 给出的工程判断

调研之后，方向逐渐清楚了。

这个 demo 不适合一上来就做很重的工作流系统。LangGraph 很适合复杂状态图和持久化执行，OpenAI Agents SDK 也有不错的 tracing 和 session 思路，CrewAI 更偏角色协作。

但这个阶段，我更想先把“一个职业 Agent 的最小闭环”跑起来。

所以最后选了一个更轻的组合：

- `FastAPI`：对外提供订单、事件、时间线接口。
- `PydanticAI`：负责构建大模型 Agent、工具调用和结构化输出。
- `SQLite`：本地持久化订单、事件、Agent run、工具调用和 heartbeat。
- `Heartbeat worker`：定期把系统状态推给 Agent，而不是把业务逻辑写死在定时器里。
- `Docker`：让这个 demo 可以被别人拉起来复现。

这套设计里，我最在意的不是“模型回答得多聪明”，而是三个工程问题。

第一，**它能不能长期运行。**

所谓 long run，不是让一次模型调用跑几个小时。真正可靠的做法，是把长时间任务拆成事件，把状态写进数据库。Heartbeat 只是一个外部节拍器，每隔一段时间把当前订单、电量、位置、异常推给 Agent，让它重新判断。

第二，**它是不是黑盒。**

我不想只看到一句“已处理”。所以系统会保存 `agent_runs`、`tool_calls`、`events`、`heartbeats`，并且给每次决策生成一个可读摘要。

但这里有一个边界：我不会暴露模型原始思维链。

系统应该返回的是安全可审计的解释，比如：

```json
{
  "decision": "notify_dispatch",
  "reason_summary": "电量低于规则阈值，继续配送存在延误风险",
  "matched_rules": ["manual.low_battery"],
  "next_actions": ["通知调度", "前往充电点", "10 分钟后复查"]
}
```

这已经足够让用户知道它为什么这么做，也能让开发者复盘问题。

第三，**它能不能换模型。**

这也是我在准备写文章前，又停下来补的一步。

## 03 写文章前，我先补了一个工程洞

本来我已经准备开始写这篇文章了。

但写到“如何运行”的时候，我发现一个问题：如果别人要复现这个项目，他不一定用官方 OpenAI，也可能用任何 OpenAI-compatible 的模型网关。

如果我只在 README 里写一个 `OPENAI_API_KEY`，这个 demo 就不够工程化。

所以我先暂停写文章，回头补配置。

现在项目里新增了一个 `env.example`：

```env
COURIER_AGENT_PROVIDER=openai-compatible
COURIER_AGENT_MODEL=gpt-4o-mini
OPENAI_API_KEY=replace-with-your-key
OPENAI_BASE_URL=https://api.openai.com/v1
DATABASE_PATH=data/courier_agent.db
HEARTBEAT_INTERVAL_SECONDS=10
LOW_BATTERY_THRESHOLD=15
```

这个小改动的意义不大，但很重要。

它意味着这个项目不是写死某一家模型，而是默认走 OpenAI 兼容协议。你可以把 `OPENAI_BASE_URL` 换成自己的网关地址，把 `COURIER_AGENT_MODEL` 换成网关支持的模型名。

工程项目里，很多“能不能用”的差别，就藏在这种小地方。

一个 demo 如果只能在作者机器上跑，那它更像截图素材。

一个 demo 如果有 `.env`、`env.example`、Docker、日志、数据库、测试和错误复盘，它才开始像一个可以持续演进的项目。

## 04 这个快递员目前能做什么

目前这个快递员 Agent 还很小。

它可以创建订单，可以接收事件，可以在 heartbeat 到来时重新判断订单状态。它有一份很短的配送手册，里面写着低电量、门禁、客户失联、天气风险这几类规则。

它也有几个工具：查手册、联系客户、通知调度、规划路线、更新记忆。

当事件进入系统后，FastAPI 不直接写死下一步，而是把订单状态、当前事件和业务手册交给 Agent。Agent 返回一个结构化决策，系统再把这个决策写回 SQLite。

这就是第一版闭环：

**事件进来 → Agent 判断 → 工具调用 → 决策落库 → 时间线可查。**

看起来很简单。

但这个简单结构后面可以长出很多东西。

比如测试篇，可以写如何让 Agent 测试不依赖真实模型。今天我跑测试时就遇到了一个真实问题：PydanticAI 初始化时会校验 provider，测试里随便写 `fake:model` 会直接失败。这个问题很适合单独写一篇：为什么 Agent 项目必须支持 fake agent 注入。

比如使用篇，可以写怎么通过 API 创建一个订单，再连续推送“低电量”“客户回复”“送达完成”几个事件，看 Agent 的决策如何变化。

比如问题修复篇，可以写为什么 README 里原来写的是 `/health`，但实际 API 路径是 `/api/v1/health`。这种小 bug 不复杂，却很真实。

比如工程化篇，可以继续写 Docker 部署、日志字段、SQLite 表结构、审计时间线，以及 heartbeat 为什么不应该直接承担业务逻辑。

所以我现在反而不急着把快递员做大。

我更想把它做成一个连续演进的样本。

## 05 为什么叫“无用 Agent”

我故意把这个系列叫「无用 Agent」。

不是因为它真的没用。

而是因为我不想一上来就讲那些宏大的词：通用智能、数字员工、千行百业、端到端自动化。

这些词太容易让人兴奋，也太容易让人误判。

真实的 Agent 落地，往往不是从一个全能员工开始的，而是从一个很小的职业切片开始。

快递员不是一个抽象职业。

他会遇到电量不足，会遇到客户不接电话，会遇到小区门禁，会遇到天气变化，会遇到路线绕行。他每天的工作不是一条完美流程，而是一连串小判断。

这正好适合拿来研究 Agent。

因为 Agent 最有价值的地方，恰恰不是执行固定流程，而是在规则、工具和上下文之间做判断。

当然，这个 demo 现在还很粗糙。

它不能真的送快递，也没有真实地图，没有真实客服电话，没有真实派单系统。它只是一个可以运行的骨架。

但骨架的价值，是让我们可以一层一层往上加东西。

先让它能配置模型。

再让它能跑测试。

再让它能复盘错误。

再让它能处理更多异常。

再让它能变成另一个职业。

这就是这个系列接下来要做的事。

---

## 06 后面准备怎么写

如果把“快递员 Agent”当成一个真实项目，我后面至少可以继续写这些篇章：

- **使用篇**：从 `.env` 配置开始，跑起 Docker，用 API 创建第一个配送订单。
- **测试篇**：为什么 Agent 项目不能直接依赖真实模型，怎么做 fake agent 和稳定断言。
- **问题修复篇**：记录真实开发中遇到的配置、路由、依赖、provider 校验问题。
- **可观测性篇**：怎么用日志、tool calls 和 timeline 让 Agent 不再是黑盒。
- **业务规则篇**：怎么把快递员手册从硬编码规则升级成可检索知识。
- **职业扩展篇**：从快递员迁移到外卖员、客服、销售、前台，哪些模块能复用，哪些必须重写。

我更希望这个系列像一个项目日志，而不是一篇“AI 又能干什么”的爽文。

因为真正有价值的，不是证明 AI 能扮演一个快递员。

而是通过快递员这个足够具体、足够日常、足够不完美的职业，把职业 Agent 的工程边界一点点摸清楚。

如果你只记住一件事，那就是：

**不要急着做一个万能 Agent。先做一个看起来很无用、但能持续运行、能解释自己、能被测试、能被修复的小 Agent。**

这可能才是职业 Agent 真正落地的开始。
